# KeepKey password bank passkey and mobile audit

Reviewed November 7, 2026. The proposed product is a bank of reproducible passwords generated by KeepKey, an encrypted registry mapping derivation locations to domains and accounts, and a small expiring cache on mobile and in the browser. BEX supplies autofill, rotation tracking, and assisted site-specific password changes. The [product design](DESIGN.md) defines those flows and the recovery contract.

The derivation groundwork exists, but the current mobile pairing is a watch-only public-key handoff. It must not carry passwords. Firmware has a real USB CTAP2 implementation; a separate desktop software-passkey experiment has different security properties and several confirmed weaknesses. BEX already has browser-driving tools, but its snapshot and typing paths currently expose password text to agent tooling and page-side diagnostics.

## Evidence and scope

This is a source audit with offline reproductions, not a penetration test or a signed-artifact certification. No account passwords were changed, pairing codes redeemed, device operations invoked, applications deployed, or sibling working trees edited. The mobile and prototype checkouts contain pre-existing uncommitted changes; the relay checkout also has an unrelated unresolved merge. Findings refer to the inspected files, not an assertion that those exact files match a deployed binary.

### Current mobile pairing flow

1. Desktop `projects/keepkey-vault/src/bun/index.ts:8198` verifies a connected wallet, reconciles cached managers against the live seed, and collects known public accounts. It refuses export when seed identity is inconclusive. BTC/EVM include tracked accounts; UTXO export checks completeness. Some other-chain failures are logged and skipped, so successful pairing can still mean a partial portfolio.
2. Desktop posts device ID, label, addresses and xpubs as JSON over HTTPS to `https://vault.keepkey.com/api/pairing`. There is no application-layer payload encryption.
3. Relay creates an eight-character bearer code with a fifteen-minute lifetime and keeps its record in a process-local Map.
4. Desktop displays `{code, url}` as QR. Mobile scans it, or accepts the manually entered code against the fixed production URL, then retrieves `/api/pairing/{code}`.
5. Mobile saves public keys and device metadata in AsyncStorage. A WebView loads the server-provided `vaultUrl`, and injected JavaScript copies the wallet data into that origin's localStorage and `window.keepKeyVaultData`.
6. Mobile unpair removes three AsyncStorage keys. It does not establish a revocable desktop-to-phone channel or erase the phone's persistent WebView data.

This exports portfolio visibility. Possession of the exported xpubs does not by itself authorize spending; it does expose sensitive account history and derivable public addresses. Importing an already exported public key cannot be undone by deleting a pairing record.

## Findings

Severity describes the current source and prerequisites. Password-cache implications are called out separately. Findings marked high are prerequisites before these components handle secrets.

### B1 High BEX exposes password values in snapshots and typing diagnostics

**Evidence:** `../keepkey-client/pages/content/src/agentDom.ts:287` copies every visible interactive input's `.value` into snapshots, without excluding password inputs. `chrome-extension/src/background/browserTools.ts:343` includes that value in MCP text. The type handler at `agentDom.ts:406` passes the first forty characters of typed text into `showThen`; lines 32–35 forward that detail to both the overlay and `panelLog`.

**Impact:** With Agent mode enabled and the authenticated browser bridge in use, a snapshot of a filled password field returns its value to the agent. Typing a password through `bex_type` also supplies it as an agent tool argument and forwards it to page-side diagnostics. The offline probe executes the original snapshot logic on a synthetic password input and confirms disclosure. It does not read any live browser.

**Required change:** Redact password, OTP and other declared secret fields across snapshots, read results, console/observer paths, overlays, screenshots and audit logs. Add an opaque secret-handle fill operation; a generic agent must not receive plaintext or the ability to route a secret to arbitrary fields. Filling a DOM field necessarily gives the destination page access to that password, so validate the browser-reported origin, document and target immediately before release. See DESIGN.md for scoped operations and rotation.

### M1 High Untrusted URLs control pairing and the WebView destination

**Evidence:** `../keepkey-mobile-expo/src/screens/QRScannerScreen.js:68` accepts any supplied HTTPS origin and preserves explicit HTTP. It validates code shape but has no production origin allowlist. At line 185 it persists `walletData.vaultUrl` from the response. `VaultWebViewScreen.js:251` uses that value as its navigation destination.

**Impact:** A malicious QR can select an attacker-operated pairing service and present arbitrary portfolio data and web content inside the KeepKey shell. The returned destination also remains unverified when the fixed-origin manual pairing path is used. Plain HTTP is allowed by JavaScript, although native OS transport policy may block it; iOS Info.plist does not globally allow arbitrary loads.

**Required change:** Validate URL types, scheme, exact canonical origin, path, redirects and returned destination; bind response identity to the expected service. Confine development HTTP to explicit development builds. Validate each public-key entry and bound payload size before persistence.

### M2 High Wallet injection has no origin guard

**Evidence:** `VaultWebViewScreen.js:71` builds a script that places all imported public keys in localStorage and a window global. The WebView at line 318 has neither an explicit navigation policy nor an origin check inside the injected script. `mixedContentMode="always"` is enabled on Android, alongside persistent cache and cookies.

**Impact:** If the WebView loads a foreign document while retaining the injection, that document receives the wallet export. The probe executes the original script with a synthetic foreign location and confirms the write. Actual navigation, redirect and frame behavior must still be reproduced on the exact iOS/Android builds. This would become a credential leak if password data reused this mechanism.

**Required change:** Check the initial URL as well as every navigation, popup and redirect; send external links to the external browser; check origin again inside any remaining public-data injection. Disable mixed content. Keep password secrets in a native credential broker, outside hosted pages and their localStorage. The WebView [navigation callback](https://github.com/react-native-webview/react-native-webview/blob/master/docs/Reference.md#onshouldstartloadwithrequest) does not cover Android's initial load, so it cannot be the only check.

### M3 Medium Unpair leaves persistent web copies and caches

**Evidence:** `VaultWebViewScreen.js:221` removes `pubkeys`, `deviceInfo` and `setup_complete` from AsyncStorage, then navigates away. The same screen enables DOM storage, cache, shared cookies and non-incognito browsing. Its injection writes four wallet storage keys, a mobile flag and an in-memory window object.

**Impact:** The native unpair operation leaves copies of the wallet data in WebView storage. That is a confirmed missing cleanup path; persistence across process restart and backup needs platform testing.

**Required change:** Clear native records, relevant WebView website data/cache/cookies, runtime references and credential-provider identities. Test unpair, re-pair with another wallet, restore from backup and reinstall. Password caches need per-entry key deletion and a separate expiry lifecycle.

### M4 Medium Pairing bearer codes use Math.random

**Evidence:** `../keepkey-vault/src/lib/pairing/PairingStorage.ts:35` draws eight characters from a 32-character alphabet with `Math.random`. The nominal space is 40 bits; it is not a cryptographic generator. The probe substitutes a controlled PRNG and reproduces `AAAAAAAA`; this demonstrates the dependency, not prediction of production codes.

**Required change:** Use a CSPRNG and substantially stronger QR invitation entropy. Treat the short human code as a separately rate-limited lookup or use a reviewed password-authenticated exchange; never use it alone as a password-bank encryption key. Remove bearer codes from logs and request analytics.

### M5 Medium Relay persistence and limits are process-local

**Evidence:** `PairingStorage.ts:22` and both pairing routes keep state in Maps. Limits use the full `x-forwarded-for` header directly. `consumePairing` deletes the record synchronously before returning; a second redemption therefore yields not-found/404, not the documented 410. The permanent store-review fixture bypasses normal limits and expiry but returns fixed demo data; no access to other pairings was established.

**Impact:** Process restart or routing POST and GET to different workers can lose valid pairings. Header-derived rate limiting depends on the deployment proxy overwriting untrusted forwarding headers. Consumption is atomic within one JS process; no same-process double-redemption race was found. A lost response after consumption cannot be retried successfully.

**Required change:** Shared bounded TTL storage with atomic consume/ack semantics appropriate to the payload, trusted client-IP extraction, distributed limits, request-size limits and non-cacheable responses. Separate demo mode from a real credential import. Verify the actual proxy and deployment topology before asserting deployed bypassability.

### M6 Medium Logs and local persistence expose portfolio metadata

**Evidence:** QRScannerScreen logs the QR/code and the full relay response; ManualPairingScreen logs the code and full response. Desktop logs the live handoff code in `index.ts:8363`. Mobile stores xpubs in AsyncStorage and WebView localStorage without an application-encryption layer. Android manifest enables backup.

**Required change:** Redact handoff tokens and account payloads, review release logging and backup behavior, and add a native application lock appropriate to portfolio privacy. Password cache keys require Keychain/Keystore protection and ciphertext storage. [Expo documents AsyncStorage as unencrypted](https://docs.expo.dev/develop/user-interface/store-data/); this does not mean the mobile OS lacks its own filesystem encryption.

### P1 High Desktop prototype stores the decryption key with credentials

**Evidence:** `../keepkey-vault-v11-passkey/projects/keepkey-vault/src/bun/passkey.ts:43` generates a random AES key and stores its Base64 form as `passkey_kek` through `setSetting`. `db.ts:337` and `:348` read/write that value in the same SQLite database that holds encrypted private keys.

**Impact:** A database copy supplies both the wrapped private keys and the key needed to decrypt them. The probe encrypts a synthetic PKCS8 key through the original engine and recovers it using the stored setting. The current engine is software-held and not seed-recoverable. The research document's proposed OS-keychain custody is not implemented here.

**Required change:** Replace custody before integration. Prefer direct firmware CTAP2 for hardware credentials. A software credential provider needs its own reviewed hardware-wrapped or OS-protected custody and backup design; changing the source of an AES key alone does not supply browser origin guarantees.

### P2 High Desktop prototype claims UV without performing verification

**Evidence:** `passkey.ts:94` sets UV unconditionally in both registration and authentication. REST approval invokes a UI approval overlay; there is no PIN or biometric verification in the inspected path. REST verification handlers also initialize approval to true if their optional callback is absent; the inspected app does install the callback.

**Impact:** A button approval is represented as user verification. The probe generates an assertion whose UV bit is set without PIN/biometric authentication in the engine. This is not evidence of bypassing the installed callback in the running app.

**Required change:** Fail closed without the verifier, bind approval to the exact ceremony, and set UV only after actual verification. Keep UP and UV distinct, as required by [WebAuthn](https://www.w3.org/TR/webauthn-3/).

### P3 High Desktop prototype is not a general website passkey provider

**Evidence:** It generates challenges locally and synthesizes `clientDataJSON.origin` as `https://${rpId}`. It does not bind a browser-verified requesting origin to an external relying-party challenge. `sign()` returns WebCrypto's raw P-256 signature directly; the probe confirms 64-byte r||s output rather than WebAuthn ES256's DER signature form. Registration approval displays body-supplied identity while the engine uses the stored challenge RP, permitting mismatched displayed and cryptographic RP values in the prototype.

**Required change:** Treat this as an experiment. Use platform credential-provider/browser integration or direct CTAP2, preserve the relying-party challenge, validate origin/RP relationships through the trusted client, bind displayed data to the stored ceremony and verify responses using an independent implementation. Do not expose a generic synthetic-origin signing service as website authentication.

## Firmware passkeys and recovery

`modules/keepkey-firmware/docs/Passkeys.md`, `lib/firmware/ctap2.c`, `ctap2_cbor.c`, `u2f.c` and `include/keepkey/firmware/passkey.h` show actual CTAP2 implementation: USB CTAPHID, ES256, ClientPIN protocol 1, checked randomness, PIN retry/throttling, presence confirmation, packed self-attestation and four discoverable slots. CTAP 2.1 management, large blobs and `hmac-secret` are intentionally unadvertised. Consequently, the current passkey interface cannot simply supply a WebAuthn PRF/hmac-secret password-vault key.

The FIDO PIN is separate from the wallet PIN. `storage_compute_u2froot` in `storage.c:154` uses the mnemonic with an empty BIP39 passphrase; FIDO credentials do not follow the desktop's active hidden-wallet passphrase. The proposed password bank should explicitly use the selected seed plus wallet passphrase instead.

**Current generation-bound passkeys are not recoverable from the seed alone.** Random hardened path data is carried in the credential ID, discoverable RP/user records live in device storage, and credential-ID authentication incorporates a random persisted reset generation. Restoring the mnemonic does not reconstruct those records or that generation. Legacy U2F migration behavior is a separate case. Do not promise password-bank recovery semantics for passkeys; current users need independently registered backup credentials or site recovery methods. A passkey-state export would also have to reconcile backups with the intended reset-invalidation guarantee.

### Release status and conflicting requirements

The local bundled manifest selects v7.14.2 as latest and v7.16.0 as beta, with a local v7.16.0 binary. The bundled README calls 7.16 a signed prerelease. That is evidence of packaging, not source-to-binary matching or successful platform tests. A web retrieval of the public remote manifest returned older values; it is not used here to settle current production firmware state.

`docs/Passkeys.md` says an anti-downgrade bootloader epoch and FIDO conformance are release gates. The explicitly authoritative `docs/release/SRS-7.16.md`, R-3.2 and R-4.3, records owner decisions that FIDO certification is outside scope and V20 may ship without an epoch; downgrade wiping is expected. The SRS still requires exact-candidate real-device migration, reset, PIN and browser/platform evidence. `docs/security/anti-rollback-security-epoch-rfc.md` remains a design RFC.

Reconcile these conflicting documents against the authoritative SRS. Do not reintroduce an approval gate the owner already removed, and do not infer certification or completed hardware gates from source presence. V20 downgrade can wipe device storage, including passkey metadata; that directly affects the recovery story.

- Firmware CTAP2/CBOR and storage migration test sources exist. The available `build/bin/firmware-unit` is older than the inspected CTAP2 source and fails locally with `exec format error`; its CMake cache points to a Linux build. **No current firmware test pass is claimed.**
- Physical iOS/Android pairing, WebView navigation/cleanup, store-artifact provenance, relay proxy topology, browser autofill, native credential-provider behavior and exact-firmware conformance remain unverified.

## Recommended implementation order

1. Fix BEX password disclosure and mobile pairing/WebView issues. Preserve existing public-wallet functionality while introducing an explicit secret-handling boundary.
2. Freeze the password-bank derivation/versioning and metadata recovery format. Implement the firmware password command with published vectors and test-device recovery before real credentials.
3. Implement encrypted profile backup, bank allocation and per-entry cache expiry. Demonstrate fresh-device restoration using a test seed and backup manifest.
4. Add BEX secret-handle autofill, account-domain binding and the rotation journal. Start rotation recipes in guided mode with verification and restart recovery.
5. Add native iOS/Android credential-provider integrations and encrypted selected-entry rehydration. Keep this separate from the watch-only pairing relay.
6. Validate direct firmware passkeys independently and retire or explicitly quarantine the software prototype's security claims.

No production implementation or deployment is included in this audit.

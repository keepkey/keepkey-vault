Reviewed candidate `4bbc479829d324bd3e94bb3383a28cfa3217f224` plus the working cancellation, WalletConnect and Monero policy fixes described below. Primary published baseline: v1.6.10, commit `88caa37014a45b154bbec8d8805f0ceffd2467eb`. Scope: device lock and cancellation, bearer authentication and approval, wallet/session ownership, address/balance cache isolation, new default-off password/Monero surfaces, provider trust, and secret persistence. Security proofs use synthetic callbacks or a scripted memory-only device; SQLite proofs use an in-memory database. One audit-command mistake touched the live preview API; it is recorded explicitly under test limits below.

Stable-release context: between v1.6.7 and v1.6.10, `auth.ts` changes only the signing-approval budget from 120 seconds to 15 minutes; authentication, pairing approval and key validation are otherwise identical. The wallet-session cache and Studio provider-key session modules are unchanged across those two baselines. This candidate adds demand-unlock/ownership handling and stricter PIN-wait traffic guards rather than removing authentication or approval requirements.

### P1 — Monero persists hidden-wallet identities

`projects/keepkey-vault/src/bun/monero-vault.ts:248` includes the effective ETH seed address and `isHiddenWallet` boolean in `watchScope`, including hidden sessions. `connect()` unconditionally calls the persistent watch store at `monero-vault.ts:493`. The store encrypts the payload, but stores `scope` and the Monero address as plaintext SQL primary-key columns (`monero-watch-store.ts:36`, `monero-watch-store.ts:64`). Thus the database itself exposes that a hidden wallet exists and links its ETH identity to its XMR address. This conflicts with the existing no-disk guarantee documented by `EngineController.isPassphraseWallet`.

Reproduction: enable Monero, enter a nonempty wallet passphrase, then connect its monitor. The isolated proof `/private/tmp/keepkey-release-security-proofs/monero-hidden-cache.test.ts` uses the actual vault and actual encrypted store with public disposable fixtures. It observes two rows (`view-key`, `address:0`) whose plaintext scope contains the synthetic hidden ETH address and `true`; its expected-zero-rows assertion fails. No private data is involved.

The boundary is broader than the watch table: `monero-vault.ts:500` passes a hidden wallet's device/address identifier into the sidecar configuration, and the send path persists pending signed transactions before relay (`monero-vault.ts:749`). A partial fix that skips only watch-store writes would leave other persistent paths. Safe short-term policy: reject hidden-wallet Monero operations before any device or persistence work; otherwise implement an end-to-end memory-only monitor, pending transaction, and sidecar policy. Monero did not exist in v1.6.10, so this is a new optional-feature privacy regression.

Implemented by the Monero owner: a shared standard-wallet-only policy checks both engine and device-state hidden classification, rejects hidden actions before lazy factory/file/store/device access, and fences subsequent work after asynchronous consent, cache, sidecar, import and relay operations. Hidden polling returns a safe empty unavailable state. Existing pending/discard recovery records are retained rather than erased. Independent review found one default-flow regression during implementation: `getAppSettings()` still touched the now-forbidden Monero factory in hidden sessions. The owner fixed it by redacting the pending count before any getter/factory call when hidden or disabled, and added actual extracted settings/factory tests. Final independent source/test review found no remaining blocker; standard-wallet monitoring and recovery remain available after switching back. Owner's combined suite/full candidate CI remain root's integration responsibility.

Owner-reported final verification: 153 tests/825 assertions across vault, failover, send, actual UI and settings gates; previous vault negative control fails six new privacy cases, settings-redaction negative control fails both hidden-settings cases. No prior recovery records were deleted. These runs were reported by the implementing owner; my independent pass inspected source and assertions rather than repeating the full suite.

### P1 — WalletConnect approval is not bound to the wallet it displayed

`projects/keepkey-vault/src/bun/walletconnect.ts:854` waits for host approval, then `walletconnect.ts:864` invokes the signing closure without checking a captured wallet session. The EVM callbacks in `index.ts:1518` and `index.ts:1521` select the current `engine.wallet` at that later point. The account/path used for the request was chosen before approval.

Reproduction: start `personal_sign` for wallet A, account 2; leave the native approval open; switch to wallet B; approve the old card. The actual `WalletConnectManager.handleRequest` proof `/private/tmp/keepkey-release-security-proofs/wc-session-switch.ts` records card A's address, but dispatches B's callback with A's account-2 path and returns B's synthetic signature. Network access is explicitly disabled. Real firmware confirmation still applies: this is an approval/session mismatch, not unattended signing.

The relevant callback and approval paths are unchanged from v1.6.10; the WalletConnect production diff adds only contract-rating enrichment. The new Desktop/REST coordinator does not cover WalletConnect callbacks. Bind each WC request to the wallet/session used for the card and recheck before every new device exchange, including after metadata/network awaits. Keep already-admitted exchanges draining under their existing owner.

Implemented working fix: each manager request and pairing proposal captures wallet handle, hardware ID, effective seed identity, hidden-wallet classification, session epoch, enabled state and manager generation. Initial scopes without a ready device and verified effective identity fail before opening a card or touching the device. Device callbacks enter the existing Engine coordinator with busy rejection; their original request assertion is composed with the acquired operation assertion. The coordinator runs outside the WC context so releasing an old request cannot leak its stale assertion into the next REST owner. The actual production host-card callback also checks its scope before and after asynchronous enrichment. Approval failures dismiss the old card.

New isolated `__tests__/walletconnect-session.test.ts`: **24 tests, 88 assertions pass**, executing the actual manager, AST-extracted production session/coordinator/card/sign callbacks, EngineController and hdwallet wire. Cases cover all captured identities, hidden-to-standard identity-null transition, unverified starting scopes despite cached account data, enrichment, device acquisition, local contention without queued replay, admitted automatic acknowledgement drain with a waiting REST owner, and stale pair approval. The exact previous manager fails all 24 cases; `/private/tmp/keepkey-release-security-proofs/wc-session-negative.log` records the negative control. Existing Seaport-WC, AdvancedMode, typed-description and signing-observation suites pass separately: **93 tests, 308 assertions**. Ephemeral-port tests required sandbox escalation; their initial bind failures are not production failures.

The same permission boundary now covers WC topics: local disconnect revokes its topic before awaiting the remote SDK, `session_delete` retires it, and missing/expired sessions fail before a new device exchange. A revoked cryptographic topic remains rejected even if stale SDK cache data still lists it. Actual `onSessionRequest` cases cover disconnection during approval, card enrichment and acquired signing enrichment, remote deletion and expiry; another dApp's topic remains valid. Already-admitted exchanges still drain under their original lease.

### P2 — Cancel during preparation can be followed by a new signing request

Default path: `SwapDialog.tsx:2555` calls `cancelForegroundDeviceOperation` and then displays “Swap cancelled”. `index.ts:4838` forwards that to `engine.cancelDesktopDeviceOperation()`. The operation has already been dispatched into `headlessExecuteSwap`, but still awaits imports, tracker initialization, provider/build work or the next signature. The former `withDesktopDeviceOperation` checked abort only before invoking the action; its abort listener canceled only an already-open device prompt. The later `beforeSign` checked the quote/session, not the operation's cancellation.

The underlying race existed in v1.6.10: its Swap Cancel called `cancelDeviceSigning` and immediately displayed cancellation, while `wallet.cancel()` did not remember cancellation through future asynchronous work. The newer scoped owner fixed pending-unlock and active-prompt cases but retained this post-dispatch/pre-wire gap.

Implemented working fix: `device-operation.ts` exports an operation context with an ownership assertion. `engine-controller.ts:268` captures abort, active owner, wallet handle, hardware identity, and effective seed. `device-gate.ts:183` creates a fresh admission context for each `call`/`lockDuring`; `device-gate.ts:201` checks it immediately before the first non-reply wire write. An earlier read cannot admit the next sign. Replies remain allowed and cannot themselves admit a cancelled new flow. Already-admitted exchanges retain their lease through their real completion.

Validation uses the actual EngineController, hdwallet `ethSignMessage`, Transport, wire framing and automatic ButtonAck with a memory-only delegate. New isolated `__tests__/desktop-operation-cancellation.test.ts`: 8 tests, 28 assertions pass. It checks zero sign writes after preflight cancellation, cancellation after an earlier read, fresh admission for a later `lockDuring`, automatic acknowledgement draining and queue ownership, another REST owner, and retired wallet/device/seed rejection. A negative control injects the exact previous HEAD method into the actual EngineController: 7 of 8 cases fail, directly observing an extra `ETHEREUMSIGNMESSAGE` wire write (type 108); the admitted-drain control remains green. Proof log: `/private/tmp/keepkey-release-security-proofs/cancel-negative.log`.

## Boundaries checked without another confirmed regression

- API listeners remain loopback-only; the main REST API uses bearer keys. `/mcp` and password-agent HTTP reject browser Origin/Sec-Fetch headers and do not inherit wildcard CORS. BEX WebSocket upgrade requires a valid pairing token. Authentication/pairing storage is unchanged from v1.6.10.
- The REST signing gate authenticates before approval, rejects empty probes, binds request cancellation to its own approval, and checks session epoch before device acquisition. Passive cache-only address/pubkey misses fail without starting PIN unlock. Setup on an uninitialized device retains wipe guards.
- The coordinator bounds its queue and timeout, rejects stale wallet/device/known-seed identities, and holds a cancelled unlock's ownership until its wire promise drains. PIN/passphrase replies and cancellation remain separately permitted. Passive Desktop reads deduplicate within verified scope; mutable managers refresh when unlocked; stale warm cache fallback is restricted to local pre-dispatch contention and cannot mask provider failures or session changes.
- REST derivation caches use live wallet-handle/device/effective-seed scope, invalidating on disconnect, passphrase transition and seed changes. Hidden-to-standard transitions are covered even without `seed-changed`. Desktop cached values are cloned rather than returned by reference.
- Password manager defaults off. Bank derivation, secret reveal and agent mutations enforce the flag and native unlocked bank. Registry data is authenticated-encrypted; owned buffers are zeroed on lock/expiry/session retirement. MCP blocks private BEX password transport names; agent results omit secret values. Browser fill requires an exact selected origin/document/ref, a one-use grant and native approval. Clipboard copy is an explicit UI action; reveal is hidden on blur/visibility change and expiry.
- Studio provider private keys remain RAM-only, AdvancedMode-gated on each entry point, and cleared on device removal/change and policy disable. Caller ERC-7730 material is removed in signing paths; runtime provider metadata still binds to the provider named on the approval card. New hosted contract ratings remain informational and cannot authorize clear-signing or substitute for device-verified schemas.
- Emulator recovery-word backup now uses a live, session-checked read and displays directly in the emulator window rather than returning words to the main renderer. Its flag, active emulator, wallet/delegate/instance/flash and ready-state checks fail closed for physical devices.

Targeted existing verification after the cancellation fix: PIN wait guards 58 tests/196 assertions; coordinator, Desktop RPC and REST wallet caches 74/210; REST demand-unlock 22/114. Together with the new suite: **162 tests, 548 assertions, zero failures** under Bun 1.3.14. `git diff --check` passes. Root owns dependency/reproducibility review and full candidate CI.

Additional security suites: password bank/device/BEX/agent 36 tests/179 assertions; MCP/BEX lifecycle 32/57; provider key/provider configuration/Bitcoin-only boundary 66/412 with synthetic providers and in-memory storage. All three final isolated commands passed.

Test boundary incident: an additional batch mistakenly included `__tests__/rest-sign-gating.test.ts`, which is a live-only fixture rather than a source-only route guard. Its `beforeAll` fetched the preview's localhost:1646 health and requested pairing as `rest-sign-gating-guard` (`url: http://localhost`), then timed out waiting for approval. No signing test ran and the fixture obtained no approved key. The coordinating agent was immediately notified to reject that specific pending pairing. This fixture is excluded from further audit execution; its failed live attempt is not counted as synthetic validation.

Limits: this is a source/security-boundary review with synthetic regression proofs, not a penetration test, firmware audit or hardware signing certification. Default-off optional features were inspected but not exercised against real daemons, browser extensions, OS keychains or remote providers. Findings and line numbers refer to the recorded candidate plus the explicitly described working fix; update their status after integration.

# Pioneer Production EVM Clear-Sign Metadata — what the server must build for 7.15.0-rc3 (Handoff, 2026-07-02)

**Picks up from** `handoff-keepkey-sdk-clearsign-coverage.md`. That handoff covers the **test**
path (key_id=3 signer loaded at runtime via `LoadClearsignSigner`, blobs generated client-side by
the keepkey-sdk device suite). **This** handoff is the **production** path: what
**pioneer-insight / pioneer-discovery / pioneer-server** must change so the blobs real users get
are actually accepted by rc3 firmware.

> One-line goal: replace Pioneer's **static, zero-tx_hash** pre-signed blob catalog with a
> **per-transaction** metadata signer (real sighash + real arg values, key_id=0 production key),
> and bring `pioneer-insight/lib/serializer.js` up to the rc3 wire format.

---

## 0. TL;DR — the production blobs are architecturally incompatible with rc3

Pioneer today ships **2933 pre-signed static blobs** (`pioneer-discovery/src/descriptors/evm-signed-blobs.json`,
generated by `scripts/sign-all.mjs`, `_meta.generated: 2026-03-31`), keyed
`chainCaip → contractAddress → selector`. Every one is signed with:

- `txHash: new Uint8Array(32)` — **ZERO hash** (`sign-all.mjs:184` literally comments `// zero hash for catalog entries`)
- `value: new Uint8Array(0)` for every arg — **no amounts**, names only (`sign-all.mjs:174`)
- `classification: CLASSIFICATION_VERIFIED` — hardcoded (`sign-all.mjs:187`)
- `keyId: 0`, prod pubkey `0218621d…` (`_meta.publicKey`, matches firmware `METADATA_PUBKEYS[0]`) ✅

rc3 firmware **fail-closes on tx_hash binding** (`signed_metadata_enforce` at `send_signature`:
the blob's `tx_hash` must equal the exact sighash the device is about to sign). A zero tx_hash
never matches a real tx → **every production blob is refused** and the device blind-signs, exactly
like the SDK's dead `ZERO_HASH` fixtures. A static catalog **cannot** fix this: `tx_hash` and the
displayed amounts depend on the *specific* transaction (nonce, gas, value, calldata args), which
don't exist at pre-sign time. **Production clear-sign requires live per-tx signing.**

---

## 1. What rc3 requires of a production blob (the contract)

Per tx, the signed metadata blob must carry:

1. **The real sighash.** `tx_hash` = keccak256(RLP of the *exact* legacy/EIP-155 tx the device will
   sign) — nonce, gasPrice (or 1559 fees), gasLimit, to, value, data, chainId. Reference impl:
   `python-keepkey@1545299 keepkeylib/signed_metadata.py:eth_sighash_legacy` (:494) /
   `eth_sighash_eip1559` (:513). If it's one byte off, the firmware refuses.
2. **Real display args** in hex-free formats — `ADDRESS`(1) / `STRING`(4) / `TOKEN_AMOUNT`(5) with
   *actual values* (the real recipient, the real "10.5 DAI"), not empty placeholders. `RAW`(0)
   renders hex on the OLED and is banned from the honest catalog.
3. **Derived classification**, signed by a key the firmware trusts (slot 0 production key). rc3
   zeroed the old built-in DEBUG key; a blanket-VERIFIED zero-hash blob is `MALFORMED`.

The offline byte-for-byte conformance oracle for all of this is
`keepkey-sdk/tests/clearsign-offline-parity.js` + `tests/fixtures/clearsign-golden.json` (51 flows,
reproduces python's frozen `REFERENCE_BLOB_SNAPSHOTS`). **Any Pioneer serializer change must keep
reproducing those snapshots** (with the caveats in §5).

## 2. Fix `pioneer-insight/lib/serializer.js` — it's behind the rc3 wire format

`projects/pioneer/modules/pioneer/pioneer-insight/lib/serializer.js` is a **compiled artifact**
(there is no `src/` or `package.json` in that dir on disk — find and edit the TypeScript source in
whatever builds it; the built file is what needs to end up correct). Two concrete gaps vs
`signed_metadata.py`:

### 2a. Missing arg formats (blocks STRING + TOKEN_AMOUNT entirely)
`serializer.js:16-19` defines only:
```
ARG_FORMAT_RAW = 0, ARG_FORMAT_ADDRESS = 1, ARG_FORMAT_AMOUNT = 2, ARG_FORMAT_BYTES = 3
```
rc3 needs (from `signed_metadata.py:19-29`):
```
ARG_FORMAT_STRING = 4        // attested printable label ("Aave V3", "5%", "3 batched calls")
ARG_FORMAT_TOKEN_AMOUNT = 5  // decimals(1)+symbol_len(1)+symbol(<=10)+amount(1..32 BE) → "1000 USDC" / "UNLIMITED USDC"
```
Add both constants and export them from `lib/index.js` (see §2c).

### 2b. Arg-value length cap 32 → 44
`serializer.js:46-47` throws when `arg.value.length > 32`. A `TOKEN_AMOUNT` value is up to **44**
bytes: `decimals(1) + symbol_len(1) + symbol(<=10) + amount(<=32)` (`signed_metadata.py:31-33`,
`METADATA_MAX_ARG_VALUE_LEN = 44`). Bump the cap to 44 or the biggest real approval amount throws
before it can be serialized. Everything else in `serializer.js` (version, chain_id 4 BE, contract
20, selector 4, tx_hash 32, method 2 BE + name, num_args, per-arg name_len(1)+name+format(1)+
value_len(2 BE)+value, classification, timestamp 4 BE, key_id) **already matches python
byte-for-byte** — verified: the JS parity gate uses this identical layout and reproduces all 51
snapshots.

### 2c. `lib/index.js` is a stub that doesn't export the signer
`lib/index.js` re-exports `serializeMetadata` + the (old) `ARG_FORMAT_*` from `serializer.js` and
`signPayload/signWithMnemonic/verifyBlob` from `signer.js` — but it is **out of sync** with
consumers: `keepkey-sdk/tests/fixtures/generate-evm-fixtures.js:17-21` imports
`serializeMetadata, signPayload, deriveSigningKey, ARG_FORMAT_ADDRESS, ARG_FORMAT_AMOUNT,
ARG_FORMAT_RAW, CLASSIFICATION_VERIFIED` from it and signs `txHash: ZERO_HASH` against firmware
key 0 — all now dead on rc3. When you add STRING/TOKEN_AMOUNT, export them here too.

### 2d. `signer.js` uses `lowS: true` — a byte-parity mismatch (not a device-reject)
`signer.js:signPayload` signs with `secp.signAsync(digest, priv, { lowS: true })` (:~40). python
(`signed_metadata.py:284`, `sign_digest_deterministic`) does **not** normalize S. Both verify fine
on-device (firmware `ecdsa_verify_digest` accepts either), so this is **not** a signing bug — **but**
it means Pioneer's blob bytes differ from python's reference vectors on ~half of any given flow set
(the JS parity gate had to pass `{lowS:false}` to match; 26/51 catalog flows differ under
`lowS:true`). If you want a byte-reproducible production snapshot suite (§5), sign with
`lowS:false`. If you only care about device acceptance, leave it — but document the choice so the
next person doesn't chase a phantom diff.

## 3. tx_hash binding — the vault→Pioneer request is missing the tx

The vault fetches the blob in `keepkey-vault/src/bun/calldata-decoder.ts:fetchPioneerSignedBlob`
(:453). It calls either `pioneer.SignDescriptor({ chainId, contractAddress, data })` (:466) or
`POST ${base}/api/v1/descriptors/sign` with the same body (:475-479). **That payload has no
`nonce`, `gasPrice`/`maxFeePerGas`, `gasLimit`, or `value`** — so Pioneer *cannot* compute the
sighash even if it wanted to. This is why the current design fell back to a static catalog.

To bind the real tx_hash, **one** of these has to happen:

- **(A, preferred) Vault sends the full tx, Pioneer computes the sighash + signs live.** Extend the
  request to `{ chainId, to (contractAddress), data, nonce, gasLimit, gasPrice | maxFeePerGas +
  maxPriorityFeePerGas, value }`. Pioneer decodes calldata → real args, computes
  `eth_sighash_legacy`/`eip1559`, serializes, signs with key_id=0, returns the blob. This is the
  real fix and matches how the device tests work (`_clearsign_flow`). **Note the chainId 0→1
  normalization** the vault already applies (`rest-api.ts:2039`) — Pioneer must hash with the
  **same** chainId the device signs (1), or the sighash won't match.
- **(B) Vault computes the sighash, sends it to Pioneer to sign.** Smaller Pioneer change (it just
  serializes+signs a caller-provided `tx_hash`+args), but moves calldata→args decoding and hashing
  into the vault. Weaker separation; also means the vault trusts itself for the "what," which is
  fine since the vault owns the confirm screen anyway.

Either way the current `{chainId, contractAddress, data}` contract at
`calldata-decoder.ts:466/475` and the corresponding server route must change. **I could not find a
live server route that serves `/api/v1/descriptors/sign`** — no `SignDescriptor` /
`descriptors/sign` handler exists in `pioneer-server` (grep returned nothing); the only signing
code is the offline `pioneer-discovery/scripts/sign-all.mjs` + the static
`evm-signed-blobs.json`. So "what serves that path today" is an open question (§7) — it may 404
and the vault silently falls through to blind-sign.

## 4. Key handling — this part is already correct, keep it

- `sign-all.mjs:75` `KEY_SLOT = 0`; `_meta.publicKey = 0218621d9c14473458713bd3e672e53480aa7032ca9b67356395e88709bb45226a`
  == firmware `METADATA_PUBKEYS[0]`. Production blobs are correctly key_id=0.
- The production master mnemonic is `pioneer-insight/.env` `INSIGHT_MNEMONIC` (mode 0600). **Never
  commit it, never log it, never move it into source.** Key derivation
  (`lib/keys/keygen.js:deriveSigningKey`) is SignIdentity `ssh://keepkey.com/insight` index=slot —
  verified byte-identical to `signed_metadata.py:_derive_insight_key`. Signing stays offline
  (the mnemonic derives the key; only the key touches the signer). Keep it that way for a live
  endpoint: load the derived private key once at boot from the env-provided mnemonic, sign in
  memory, never expose it.
- Derivation-index vs key_id-slot are **different namespaces** (`keygen.js` header + the sibling
  handoff): the test key is derived at identity **index 0** of the *test* seed but embedded as
  **key_id=3**. Don't "fix" this by deriving at index 3. Production = index 0 of the *production*
  seed, key_id 0.

## 5. Conformance gate for Pioneer

`clearsign-golden.json` / `clearsign-offline-parity.js` prove serializer+sighash+signer parity, but
they're signed with the **test key (key_id=3)** and `lowS:false`. Pioneer signs with the
**production key (key_id=0)** and currently `lowS:true`, so its blobs will **not** sha256-match
those snapshots. Two honest options:

1. **Structural parity only:** run the golden flows through the *updated* Pioneer `serializeMetadata`
   and assert the **unsigned payload** (everything up to the signature) byte-matches python's
   payload — this catches the STRING/TOKEN_AMOUNT/44-cap correctness without needing the signature
   to match. Cheapest, no key material, do this first.
2. **Full production snapshot set:** re-run python's vector generator (or the JS gate) with
   `key_id=0` + the production key + `lowS:false` to mint a Pioneer-specific
   `REFERENCE_BLOB_SNAPSHOTS`, and assert Pioneer reproduces *those*. Only worth it if you want
   end-to-end byte reproducibility of production blobs.

Then the real gate is on-device: load a tx through the vault, confirm the OLED shows decoded
who/what/why (not raw hex), sign, and recover the signer == device address (matches
`test_msg_ethereum_clear_signing.py:_clearsign_flow`).

## 7. Open questions
1. **What serves `/api/v1/descriptors/sign` today?** No live handler found in `pioneer-server`
   (grep empty). Does it 404 (→ vault blind-signs), or is there a route I missed? Confirm before
   estimating the live-endpoint work.
2. **Approach A vs B** (§3): full tx to Pioneer, or vault computes the sighash? A keeps the "what"
   decoding centralized in Pioneer (one source of truth for all clients); B is a smaller Pioneer
   change. Recommend A.
3. **Per-tx latency budget.** The vault currently races Pioneer with a 3s timeout
   (`calldata-decoder.ts:429/435/462/467`) and falls through on miss. A live signer must fit that
   budget (decode + hash + sign) or the vault silently blind-signs. Is 3s enough, or does the
   signing path need its own budget/precompute of the static parts?
4. **1559 vs legacy.** The device tests are all legacy (gasPrice). Confirm Pioneer computes the
   correct sighash variant per tx type (`eth_sighash_eip1559` for maxFeePerGas txs).

### Honesty notes
- The serializer byte layout is verified correct against python (via the JS gate) **except** the
  two additive gaps in §2a/§2b — those are the only structural changes needed.
- The `lowS` item (§2d) is a **byte-parity** concern, **not** a device-acceptance bug. Don't rip it
  out expecting to fix a signing failure; verify on-device first.
- I did **not** run anything against Pioneer or a device for this doc — it's a static read of
  `pioneer-insight/lib`, `pioneer-discovery/scripts/sign-all.mjs` + `evm-signed-blobs.json`, and the
  vault's `calldata-decoder.ts`/`rest-api.ts`. The "no live sign route" claim is a grep-negative,
  not a proof of absence — see open question 1.

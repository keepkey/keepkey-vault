# KeepKey Volumes

## Product scope

A person chooses a storage location in Vault, creates a small encrypted volume, and opens it once per mount with a KeepKey. While it is open, ordinary applications use the mounted filesystem. The KeepKey can be unplugged. After locking or disconnecting the storage, opening it again requires a fresh approval. Existing files on the outer drive stay where they are. Formatting a drive, encrypting existing files in place, and full-disk encryption are outside this flow.

The desktop and firmware behaviors below are proposed acceptance criteria. Today's v1 firmware shows **Encrypt Key Value**. Vault already shows the corresponding public ID and asks the OS to confirm mount and lock. The stronger creation check, named firmware prompts, and physical recovery trials below are release requirements still to be demonstrated.

## What the person sees

| Moment | Vault | KeepKey |
| --- | --- | --- |
| Select storage | Show the user's drive label first, with hardware model, internal or removable location, available space, and any permissions or missing OS features. Put **Create volume** on each eligible location. Explain what stays outside the volume. | No prompt. |
| Create | Ask for the protected volume name and maximum size. Show the chosen drive and explain when space is allocated. Prevent a name collision. Show progress through approval, creation, verification, and cleanup on failure. | **Create volume?** Show the name and a stable ID the user can match in Vault. Confirm and cancel are available. |
| Verify creation | On the final storage location, use the already approved credential to open the new volume, check the expected filesystem, and confirm it locks again. Only then report **Created and locked**. Keep this check private so an empty test mount does not appear as the user's working folder. | No second approval. Creation verification belongs to the same operation. |
| Unlock | Identify the package and select its native backend. Show **Waiting for KeepKey**, **Opening volume**, then **Unlocked** only after the OS reports a mounted filesystem. Open that location. Keep **Open drive** and **Open protected volume** distinct. | **Unlock volume?** Show the enrolled name and stable ID. One volume approval per mount. A locked device may first need its PIN or wallet passphrase. |
| Use | Show the actual mount location and **Lock**. Explain that files here are accessible to authorized processes while mounted. The OS handles encryption during reads and writes. | The user can unplug the KeepKey. |
| Lock and eject | Confirm the OS detached or closed the encrypted backing. If files are busy, keep the real state visible, explain how to close them, and offer retry. After storage removal, reconcile from the OS. A reconnected drive starts locked. | No prompt to lock. |
| Recover | Discover a complete package on another supported computer, identify its format, and offer the normal unlock. Explain which public recovery files to keep together with the image and how to back them up. | A replacement device restored with the same seed and exact optional wallet passphrase gives the normal unlock prompt. No per-volume registration or original device is required. |
| Back up or retry | Identify the whole locked package for copying. Offer a new name for a practice retry, or **Delete volume** to discard the selected copy and reuse its name. The separate delete confirmation identifies the volume, its location, and what will be lost. | No hardware approval for copying or deleting a detached package. |

## Firmware contract

- Add a versioned volume capability and typed create and unlock requests. Firmware supplies the action text and limits labels to what the physical display can safely render. Compare the same stable identifier on desktop and device. Test long names, look-alike characters and truncation on the actual screen.
- For newly enrolled names, have the device generate a fresh volume ID during creation and authenticate the approved name, ID and format version with a seed-derived key that never leaves the device. Store the public record next to the image. Verify it on unlock. A desktop-supplied folder name, drive model or path alone cannot establish identity. A filesystem rename must preserve access and the enrolled name.
- Keep the credential stable across create, unlock, replacement hardware and Vault updates. Keep volume keys separate from passwords and passkeys. Use a distinct volume-only derivation for any new format promising authenticated enrollment. Design and review the exact wire format, key derivation, record encoding and test vectors before assigning a new format version.
- Preserve the v1 derivation byte for byte. A capable device can show a volume-specific approval with the v1 ID, but a v1 record has no authenticated name. Older compatible devices keep the existing v1 approval flow. For a new format requiring the dedicated firmware feature, show the minimum capability before creation or unlock. Cancellation or a failed record check ends the request.
- The device authorizes release of a credential to this computer. Vault owns the lifecycle of that credential and must keep it out of UI, logs, Keychain, command-line arguments and cross-mount caches. The device cannot establish whether the desktop actually mounted a disk or which physical USB holds a copy.

## Failures and recovery

Separate device cancellation or disconnection, missing or altered recovery metadata, incompatible firmware, unsupported OS or native format, OS permission denial, insufficient space, credential rejection, unrecognized image, explicitly reported corruption, and a busy or failed mount. Report the last confirmed state, the failed step and an action the person can take. Preserve the original package. Show **Open protected volume** if only the file manager failed after a confirmed mount. A retry rechecks the selected storage and package. Retrying creation uses a new name or a verified empty destination and cannot replace an existing package.

The record on the outer drive must be readable before unlock. It is public and does not unlock the image on its own. Recovery requires an intact encrypted image and its record, a compatible OS, and a compatible KeepKey restored with the original seed and optional passphrase. A seed cannot reconstruct missing disk data. V1 has no separate offline password issued to the owner. If access without any KeepKey becomes a product requirement, design an explicit, optional recovery credential and its backup experience.

## Native external APFS volumes

Treat **Encrypt existing files** as an operation on the selected external APFS volume. Show its name, parent device, capacity and used space before confirmation. Enumerate all volumes on the device so the person can see which data will be protected. For exFAT, explain that moving to encrypted APFS requires copying files elsewhere, erasing, and restoring. Keep native volumes distinct from image packages in the UI. The package **Delete volume** action has no equivalent in this workflow.

- Preflight the external, non-startup volume and recheck its APFS identity immediately before any change. Use the APFS volume UUID as the candidate recovery input. Prove on disposable media that the UUID survives conversion, is visible while locked, and resolves on another Mac. Never derive from the drive label, mount path, USB enclosure serial, or transient disk number.
- Version and document the native APFS derivation separately from image credentials. Determine how a fresh installation recognizes that derivation before the password is available. A public recovery record stored only inside the encrypted volume cannot serve this purpose. Test discovery with no Vault data copied from the original computer.
- macOS provides `diskutil apfs encryptVolume`, `unlockVolume`, and `lockVolume`. Use stdin for supported password input and confirm the target again after KeepKey approval. Surface conversion progress from macOS and refresh state after a restart or reconnect. Show **Encrypting**, **Encrypted**, **Locked**, and **Mounted** from OS state. A successful command can mean the conversion has started in the background.
- Verify the recovery method before starting conversion. Independently test a native password if offered, including whether external APFS supports an additional usable credential. Restoring the seed and optional passphrase on another KeepKey must reproduce the credential on a fresh Vault installation. Named firmware confirmation should follow the volume approval contract above.
- Rehearse on a plain APFS practice volume with a test file. Verify the file after conversion, lock and reconnect, cancel one unlock, and confirm a second unlock mounts the same volume. Repeat recovery on another Mac and KeepKey before using the flow on the 8 TB SSD.

## Release checks

- Run the normal Vault UI on a real Mac, Windows 10 and 11 machines, and a supported Linux desktop. Test internal storage and removable media for each supported backend. The current backends are macOS APFS disk images, Windows BitLocker VHDX, and Linux LUKS2/ext4. Windows Home currently has drive browsing only. Writable Home support needs its own backend decision and tests before claiming general Windows coverage. Verify unsupported editions and missing components show an explanation before the person approves anything. An exFAT outer drive does not make all inner volume formats interchangeable.
- On each supported setup create a small volume, write a recognizable file, confirm lock, eject and reconnect, cancel an unlock, then approve a fresh unlock and compare the file contents. Check the number of physical approvals and the resolution of the file manager destination. Test duplicate clicks, busy files, unplug during an operation, and app restart with a mounted or detached volume.
- On a second computer with a fresh Vault installation, open a copy using a second physical KeepKey restored from the same **test seed** and optional passphrase. Exercise the wrong wallet, altered or missing metadata, an unreadable copy, and legacy v1 volumes. A failed trial must preserve the only copy.
- Keep separate evidence for automated synthetic-credential tests and physical-device trials. Record the OS, app version, firmware build, storage format, and outcome. Before relying on a volume as the only surviving copy of data, demonstrate the complete lock, reconnect and recovery sequence on the intended setup.
